# SPEC: Desktop app (0.5.0 to 0.7.0)

## Goal
Turn the command-line booker into a desktop app that a resident can install, set up and leave
running, without editing files or reading English logs. The booking engine stays what it is:
it wins the 06:00 race unattended. The app adds setup, settings, a schedule switch, history
and an activity log around it. Decided between 2026-10-10 and 2026-10-12.

## Product decisions

### Where it runs
Desktop only, on the PC that runs MuMu. Inside it is a web UI (React) talking to a local
backend (FastAPI on `127.0.0.1`), so phone access over home Wi-Fi could be added later without
a rewrite. Not now: the PC sleeps most of the day, and phone access would need a login and a
firewall rule. The screens are laid out for the desktop window only: the 0.7.0 window gets a
minimum width, so no screen needs a phone layout. A phone layout comes with phone access,
later (decided 2026-10-15).

### Screens
Mockups in the "Vé giấy" style, with real data from the 2026-10-08 to 2026-10-12 runs:
https://claude.ai/artifact/9U4RU81bLsyEaD9G6Crapr (page "Toàn bộ màn hình"; private).

| Navigation (VI / EN) | Content |
|---|---|
| Tổng quan / Overview | One-line status (ready, or the one thing to do first), next booking as a ticket, last real booking per slot; while a run is in progress, its live steps |
| Hẹn giờ / Schedule | Step 1 dry run (must pass once); step 2 daily schedule switch; habits the PC needs |
| Lịch sử / History | Real bookings of a month by play date, month picker; dry runs only in the Activity log |
| Nhật ký / Activity | The 30 newest runs; per run: plain steps and "technical details" (raw log) |
| Cài đặt / Settings | Two tabs: "Đặt sân" (slots, court, day) and "Thiết lập máy" (the user's steps, auto setup) |
| Hướng dẫn / Guide | Four steps to start, what each screen does, troubleshooting; static, no request |

An app not used yet opens on Welcome instead of the Overview. It is told from the status,
never from a stored flag: no dry run has passed, the schedule is off and nothing is running
(decided 2026-10-14). The Overview sends the user there once per opening of the app, so
"Để sau" leads back for good until the app opens again (decided 2026-10-15). Welcome hides
the navigation and has four steps: an introduction (what happens every morning, what to
prepare), then device setup, booking settings and schedule, the same screens as in Settings
and Schedule. Any step can be opened, none has to be finished, but slots chosen and not
saved hold "Tiếp" back. Otherwise the app opens on the Overview, and every screen stays
reachable from the navigation; the Guide links back to Welcome.

### Device setup
Only the environment, done once; run-time steps stay invisible.

- **Done by the user**, detected by the app, with a guide: (1) install MuMu Player,
  (2) install Vinhomes Resident inside MuMu (needs a Google account in MuMu), (3) log in to
  the app. The app never reads or stores passwords. The app check needs MuMu running
  (`unknown` otherwise); being logged in is shown by the dry run (exit code 4), which the
  schedule requires anyway, so no extra app start is needed.
- Each item reports `ok`, `fixed`, `fixable` (auto setup can fix it), `user` (only the user
  can) or `unknown`; item keys and statuses are message keys for the UI.
- **"Thiết lập tự động" (Auto setup)** does the rest, skipping what is already right and
  reporting each item as already right, fixed, or not fixable (with a manual guide):
  1. find the MuMu install folder and save it to the config;
  2. set MuMu instance 0 to 540x1600 at 220 DPI (`MuMuManager setting`, as in the 0.3.0 spec;
     MuMu must restart to apply, so the user is asked first);
  3. allow wake timers on AC and battery (`powercfg`).
- **Silent, on every run** (already in the engine): start MuMu, connect ADB, install the
  uiautomator2 agent, restart the app, correct the clock with NTP, keep Windows awake.
  **Added:** turn off Android animations (`settings put global window_animation_scale`,
  `transition_animation_scale` and `animator_duration_scale` to `0`, the same as
  Accessibility > Remove animations; no developer mode needed). **Added for the app:**
  create the data folder, a default config, and the database.
- **Not part of setup:** time zone, ADB, an internet check (a network failure at 06:00 is
  logged), the sleep type of the PC, the monthly booking quota.

### Settings
The app is for the resident, who picks from ready-made choices: the slots (toggles for the
13 slots, numbered in booking order), the court (S6, S8, S9, S10) and the day (today + 0
to 2). Changes apply from the next run. Everything else is the developer's job and stays in
`config.toml`: the wake and start times, the Vinhomes app labels, fallback tap points,
package name and timeouts (decided 2026-10-15; the mockup's "Nâng cao" part was dropped).
The developer also keeps the slot and court lists in step with the Vinhomes app.

### Schedule
The dry run walks the whole flow and stops before "Xác nhận". Scheduling is allowed once a dry
run has passed. The switch creates or removes the Task Scheduler task (wake time, start time,
daily). Reminders: the PC must sleep, not shut down; stay signed in to Windows; plug in a
laptop.

### History and activity log
One SQLite database holds both. Every run writes to it, whoever started it (the 06:00 task,
the dry run button, the command line); the UI only reads it. History is one row per run with
the result of each slot; the activity log is one row per step or app event (Auto setup,
schedule on/off, settings saved, errors), including the technical log lines. Everything is
kept. The text log files stay for debugging.

### One run at a time
Only one task may drive MuMu. The 06:00 run, a dry run, Auto setup and command-line runs take
a lock; viewing pages and saving settings do not. The lock is a file holding the process id
and start time; a lock whose process is gone is removed and logged. Rules:

- No dry run or Auto setup may start between the wake time and 5 minutes after the start time.
- If the 06:00 run finds the lock held, it waits; if the lock is still held 2 minutes before
  the start time, it stops the other task, logs it and goes on.
- While a run holds the lock, the UI shows "running" and disables dry run and Auto setup.

### Language and design
- Vietnamese and English from the start, Vietnamese by default, with a switch. Every UI string
  lives in translation files. Code, the technical log layer and docs stay in English; the
  Vinhomes app labels stay Vietnamese. The chosen language is kept in the WebView's storage,
  not in `config.toml`, so the 06:00 run never depends on it.
- Visual identity "Vé giấy" (paper ticket): warm grey ground `#E7E6E1`, paper cards
  `#F8F7F3`, ink `#1C1B19`, muted text `#5C5850`, stamp blue `#2B48A6` (booked), orange-red
  `#C2410C` (failed), ball yellow `#E6F24F` (highlight); Bricolage Grotesque for text,
  IBM Plex Mono for data. The next booking is a ticket with a torn stub; booked slots carry
  an upright "ĐÃ ĐẶT" stamp; history reads like a dotted ledger. No UI kit, no gradients, no
  emoji icons. Light only: the design is paper, there is no dark theme.
- The design tokens (`ui/src/styles/tokens.css`) keep the mockups' values, with one change:
  failed text is `#B53C0B`, because `#C2410C` reaches only 4.14:1 on the ground and every
  text color must reach WCAG AA (4.5:1). The mockups have no focus style; keyboard focus
  shows a 3 px stamp-blue ring.

## Architecture

### Three processes
```
Task Scheduler (05:50) ──► booking engine (CLI) ──┐
UI "Chạy thử" ─► backend ─► booking engine (CLI) ─┤  writes  ┌────────────┐
                                                  ├────────► │ booker.db  │
Auto setup ────► backend (same process) ──────────┘          │ config.toml│
                                                             │ logs/      │
React UI ◄── HTTP + WebSocket ◄── backend (FastAPI) ◄── reads └────────────┘
```

- **Booking engine**: today's `court_booker` CLI. The 06:00 task runs it with no UI open. The
  backend also starts it as a subprocess for a dry run, so a dry run uses exactly the code path
  of the 06:00 run and a crash in it cannot take the backend down.
- **Backend**: FastAPI on `127.0.0.1`, started by the desktop app. It reads and writes the
  config, runs device checks and Auto setup, switches the schedule, starts dry runs and serves
  history and activity. Live progress is new database rows pushed over a WebSocket.
- **UI**: React in a Tauri window; it only talks to the backend.

### Data
- Location: `%LOCALAPPDATA%\CourtBooker\` for the installed app (`config.toml`, `booker.db`,
  `logs\`, the lock file). The command line keeps `--config`; development may point it at
  the repository.
- `config.toml` stays the settings store, so the CLI and the app share it. The backend writes
  it with `tomli-w` and validates it with the existing `load_config` rules.
- `booker.db` (stdlib `sqlite3`, no ORM; schema version in `PRAGMA user_version`, migrated on
  start; write-ahead logging, so the app reads while a run writes):
  - `runs`: id, trigger (`scheduled`, `dry_run`, `manual`), dry run, app version, started and
    finished time, play date, court, status (`running`, `ok`, `partial`, `failed`,
    `interrupted`), error.
  - `run_slots`: run, slot, ok, reason (when it failed), finished time, seconds, device
    commands.
  - `events`: run (empty for app events), time, category (`step`, `slot`, `error`; the app
    adds `setup`, `schedule`, `settings`), kind (the event kind, also the message key of the
    translated plain step) and its data as JSON.
  - `log_lines`: run, time, level, message: the technical layer, captured by a logging
    handler, including the failure screen dump. Lines logged before the run starts are
    stored with it.
- A database error never stops a booking: history is turned off for the rest of the run and
  the error is logged. A write takes about 0.13 ms (10-13 ms per dry run on 2026-10-13).

### Events from the engine
The engine reports progress through an event sink instead of only logging: run started,
MuMu ready, app ready, waiting for the start, booking started, slot booked or failed, run
finished. Sinks: the log (today's behaviour) and the database. Tests use an in-memory sink.
The booking flow and its command count do not change.

### API (as built in 0.5.0)
`court-booker serve` runs it on 127.0.0.1 (port 8765); OpenAPI at `/api/openapi.json`.
Errors answer `{"error": code, "detail": message, "problems": [...]}` with a stable code
(`not_found`, `lock_held`, `dry_run_required`, `bad_request`, `invalid_request`,
`invalid_settings`, `device`, `app_not_ready`, `schedule`, `engine`).

| Method and path | Purpose |
|---|---|
| `GET /api/health` | The backend answers, and its version |
| `GET /api/status` | The Overview: the run going on, schedule and next booking, last run, last auto setup |
| `GET`, `PUT /api/settings` | Read and save the booking settings (checked first; Telegram keys hidden) |
| `GET /api/setup` | Device setup checks |
| `POST /api/setup/auto` | Auto setup (`restart_mumu`); 400 in the quiet time, 409 while a run holds the lock |
| `GET`, `PUT /api/schedule` | Schedule state and next booking; switch on (needs a passed dry run) or off |
| `POST /api/runs/dry-run` | Start a dry run in its own process (202) |
| `GET /api/runs`, `GET /api/runs/{id}` | History (play month, trigger, paging); one run with its slots, steps and log lines |
| `GET /api/events` | Activity, newest first, filtered by category |
| `WS /api/live` | Each new step as `{"type": "step", "step": ...}`; `?after=<id>` resumes |

The UI reaches the backend on its own origin: Vite forwards `/api` (the WebSocket too) in
development. The desktop app (0.7.0) loads the UI from Tauri's own origin, so it must either
let the backend serve the built UI or give the client the backend's address and allow it in
CORS; that choice belongs to 0.7.0. Every error reaches the UI as a stable code with a
message in both languages; `unreachable` means no backend answered. The live feed resumes
after the last step it saw and gives up on a socket that does not open within 5 s.

### Tech stack
| Layer | Technology | Role |
|---|---|---|
| Engine | Python, uiautomator2, ADB, MuMuManager, Task Scheduler, `powercfg` | Booking, emulator, schedule, wake timers |
| Backend | FastAPI, Uvicorn, Pydantic | Local API and WebSocket, request validation |
| Backend | `sqlite3`, `tomli-w` | History and activity; writing the config |
| Backend | pytest, FastAPI `TestClient` | Tests without a device |
| UI | React, TypeScript, Vite | Screens, types, dev server and build |
| UI | React Router, TanStack Query | Navigation; API calls and caching |
| UI | react-i18next | Vietnamese and English |
| UI | openapi-typescript, openapi-fetch | TypeScript types generated from the backend's OpenAPI schema; requests typed by them |
| UI | Hand-written CSS with the design tokens; self-hosted fonts | Own identity, works offline |
| UI | Vitest, Testing Library, ESLint, Prettier | Tests, lint, format |
| Desktop | Tauri, PyInstaller sidecar | Window; the backend and engine as one `.exe` without Python |
| Release | NSIS or MSI installer, GitHub Actions | Installer built on each version tag |

The development machine needs Node.js from 0.6.0 and Rust from 0.7.0.

## Out of scope
Phone access, Telegram setup, the monthly quota, a health check before 06:00, fallback slots
or courts, installing MuMu or the Vinhomes app, logging in for the user, importing history
from the old log files, several accounts in parallel (after the UI phase).

## Verification
- 0.5.0: unit tests for the sinks, database, lock rules and API with fakes; a dry run and a
  real 06:00 run write correct history; the booking round still costs 16 commands in tests.
- 0.6.0: component tests per screen; every screen checked in both languages against the
  mockups, at desktop width (1280 px).
- 0.7.0: a clean Windows user installs the app, completes setup, passes a dry run and books
